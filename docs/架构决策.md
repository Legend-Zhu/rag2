# RAG² 架构决策（v1.0 — 最终版）

> **状态**：方向锁定，后续实现以此为准
> **决策日期**：2026-07-26
> **修订原因**：多轮讨论后，从"纯 agentic 推翻 RAG"修正为"推理驱动 + LLM 构造搜索引擎级索引"，更务实、更配得上论文级 contribution

---

## 一、Thesis 的真正诉求（初心校准）

**不是**：RAG 已死，agentic 当立（技术站队）
**而是**：传统 RAG demo 漂亮但生产废——**问题在生成物不可用**（幻觉、无溯源、不一致），不在检索精度本身。RAG² 把工程重心从"retrieval 调优"迁移到"**让生成物有用**"，哪怕成本高一点。

**标题维持**：`RAG²: From Retrieval-Augmented to Reasoning-Augmented Generation`
- "From X to Y" 是**升级/演进**，不是抛弃。向量检索可用、agentic 可用、生成都可用——但工程重心要重新分配。

---

## 二、为什么之前的 C1（grep/read/symbol_jump）不够

之前的 C1 = "文档语料上的 coding agent 换皮"。问题：
- grep 是朴素字符串匹配，无语义、无排序学习
- embedding 召回质量远不如成熟搜索引擎
- **本质上是工业界已做烂的形态，不值得写论文**

**对比基线**：网页搜索引擎能在 10¹¹ 量级互联网里毫秒级找到高匹配内容。这才是"检索的真本事"。

---

## 三、核心创新：推理驱动的检索编排（C1+C2 闭环耦合）

**Google 的局限**：搜索再精准，也只是"匹配查询词"，不理解为什么查、够不够、要不要继续。返回 10 条就完了。

**RAG² 的 C1**：把"搜索引擎的精准召回"和"推理的判断力"闭环耦合——

```
传统搜索引擎:  query → 召回 → 完（用户自己判断）
编码 agent:    query → grep(粗糙) → LLM 判断 → loop
RAG² 的 C1:   query → 推理出"需要什么事实"
                     → 调用精准检索（C2 的 LLM 构造语义索引，召回 ≈ 搜索引擎）
                     → 推理判断"够不够、缺什么、要不要继续"
                     → 按推理计划继续，直到确信
```

**两个支柱缺一不可**：
- 只有精准检索没有推理 = Google（用户自己判断）
- 只有推理没有精准检索 = coding agent 换皮（不值得论文）
- **推理驱动 + 搜索引擎级索引 = RAG² 的真本事**

---

## 四、系统架构（最终版）

```
                    ┌─ 推理规划器（C1 loop 工程，4 种策略）
                    │
query → C1 编排器 ──┤  ┌─ 后端 A: 纯 LLM 判断式（最准最贵）
                    └─→ C2 检索后端 ──┼─ 后端 B: 语义索引 embedding（hypothetical-Q 向量化）
                                       └─ 后端 C: 混合（B 粗筛 + LLM 精排）
```

### 两个正交维度（构成论文 ablation 矩阵）

**C1 loop 策略（4 种）**：
| 策略 | 机制 | 预期优势 | 预期劣势 |
|------|------|----------|----------|
| S1 纯 ReAct + 极致工具 | 模型自主，无额外机制 | 成本低、纯粹 | 多跳易漂移 |
| S2 ReAct + 反思重规划 | 每 N 步反思总结 | 抗漂移、适合多跳 | 多耗 token |
| S3 ReAct + 并行分支 | 多路径探查汇合 | 覆盖广、抗失败 | 成本数倍 |
| S4 预设策略 + 固定 loop | 按问题类型路由 | 可控、便宜 | 需人工设计 |

**C2 检索后端（3 种）**：
| 后端 | 机制 | 召回质量 | 成本 |
|------|------|----------|------|
| A 纯 LLM 判断 | LLM 看所有 hypothetical_questions 选最相关 | 最高 | 每题贵 |
| B 语义 embedding | 对 hypothetical-Q 和实体做 embedding 检索（非原文） | 高于传统 RAG | 中 |
| C 混合 | B 粗筛 top-20 + LLM 精排 top-5 | 高 | 中高 |

**论文核心实验**：4 策略 × 3 后端 = 12 组合（实际跑关键组合，其余讨论）

## 五、C1/C2 关系（重要修正）

| 之前理解（错） | 现在理解（对） |
|----------------|----------------|
| C2 是 C1 的"地基"，弱关联 | **C2 是 C1 检索能力的核心引擎**，必须做到搜索引擎级召回 |
| C2 可选，作为消融 | **C2 是必需**，C1 多跳能力全靠它 |
| 三支柱并列替代 RAG | 三支柱共同实现"让生成物有用" |

## 六、C2 完整索引规格（升级版）

入库阶段（一次性，离线，缓存复用），每文档生成：

| 标注 | 说明 | 用途 |
|------|------|------|
| **假设性问题集**（HyDE 倒置） | 5-10 个"这段能回答的问题" | 后端 A/B/C 的核心检索锚点 |
| **实体-关系三元组** | subject-relation-object，不止实体名 | 多跳推理路径 |
| **跨文档实体共现图** | 同实体在哪些文档出现 | 多跳路径推荐 |
| **实体类型分类** | person/location/org/date/concept | 精确过滤 |
| **多粒度摘要** | sentence / paragraph / document 三层 | 摘要先导检索 |
| **相关性自述** | "何种查询下应被召回" | 后端 A 的判断信号 |

**成本（可接受）**：每文档索引构建 completion ~800-1000 tokens。n=100（2000 文档）索引构建总 token 约 3-4M，一次性的，缓存复用。

## 九、与 E0 的关系（降级）

E0（长上下文 vs RAG 拐点）已完成 n=30，结果：
- 10³-10⁵：LC 与 RAG 持平或反超（access 在中等规模已非瓶颈）
- 10⁶：LC 全 overflow（窗口硬边界）

**E0 的角色**：立论铺垫，证明"access 已非瓶颈 → RAG 应重构重心"。n=30 已够讲清故事。
**n=100 是否补做**：降为 P2，不阻塞主线。重心移到 C1+C2 的真本事。
