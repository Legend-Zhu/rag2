## 修订说明（2026-07-26，W1 已完成验收后补充）

本方案是 W1 启动前的设计文档，方向总体正确。W1 执行后有以下**实测发现**需补充：

1. **K3 温度是硬约束**：API 仅接受 `temperature=1.0`，传 0/0.5 直接报 400。gateway 已用 `forced_temperature` 自动覆盖。可复现性靠请求级缓存保证。
2. **Qwen3.8 thinking 模式强制开启**：`enable_thinking` 报 "restricted to True"。completion token 含思考过程（约答案可见 token 的 3-5 倍）。这是 thesis H1/H2 的时代佐证——reasoning-first LLMs 已成主流。
3. **配额模型修正**：实际是 **token plan 订阅制**（K3 和 Qwen3.8 各自独立池），不是按量计费。Qwen3.8 七天配额约 33M，按周刷新。夜间 2 折起省配额。"成本"维度应理解为 token 配额消耗，不是钱。
4. **W1 实际提前 6 天完成**（原计划 8/9，实际 7/26 第一天）。详见 `W1-验收报告.md`。
5. **架构方向有重大演进**：W2 的 C1/C2 形态已重构。**C2 是 C1 的检索引擎（非可选消融）**，C1 不再是 grep/read 工具集而是"推理驱动的检索编排器"。详见 `架构决策.md`。

**结论**：本方案描述的共享层（ModelGateway/DataLoader/baselines/Evaluator/Runner）已实现且验收通过，可继续作为基础设施。但"C1/C2/C3 是三支柱并列"的描述已过时，以架构决策.md 为准。

## 二、关键设计决策

### 决策 1：模型接入——配置驱动的统一抽象

K3 与 Qwen3.8 **均兼容 OpenAI 与 Anthropic 两套 API 协议**。这意味着：

- **不需要为每个模型写专用 client**。两者都能通过"协议适配 + endpoint 配置"接入。
- **推荐主路径**：统一走 **OpenAI 兼容协议**（`base_url` + `api_key` + `model_name` 三件套配置）。OpenAI SDK 生态最成熟、工具调用 / 流式 / 长上下文支持最全，且两个模型都兼容它。
- **备选路径**：保留切到 **Anthropic 兼容协议**的能力。原因——某些能力（如超长上下文的分页、特定工具调用格式）在两套协议下行为可能不一致；若 OpenAI 兼容层在某模型上出问题，可单模型切到 Anthropic 协议而不影响其他模型。

**抽象成一个 `ModelGateway`**：上层只看到 `generate(messages, tools, model_config) → response`，不关心底下走哪条协议、哪个 endpoint。`model_config` 由 YAML 指定：

- `model_name`（如 `kimi-k3` / `qwen3.8`）
- `protocol`（`openai` / `anthropic`）
- `base_url`
- `api_key_env`（环境变量名，不硬编码）
- `max_tokens`、`temperature` 等推理参数

**角色解耦**：同一模型可扮演"生成器"或"验证器"，由配置决定，不在代码里写死。这是 C3 跨模型对照实验的前提——`generator: kimi-k3, verifier: qwen3.8` 只是改配置。

### 决策 2：缓存是一等公民（API-only 专属）

每次 API 调用都付费，**任何重复调用都是浪费**。强制设计：

- **请求级缓存**：以 `(model, messages, tools, params)` 的稳定哈希为 key，响应落盘（JSONL 或 SQLite）。相同请求直接读缓存，不付费、不重跑。
- **索引级缓存**（为 C2 预留）：生成式索引产物按 `corpus_hash + model + config` 缓存，W2 直接复用 W1/后续的产物。
- **可复现性副产物**：缓存本身就是实验记录，论文 appendix 可直接引用 hash 证明可复现。

**代价**：prompt 任何微小改动都会 miss 缓存。W2–W4 调 prompt 时要接受"重跑成本"，或用版本化 prompt（prompt 加版本号入 hash）。

### 决策 3：子采样固定化

每个 benchmark 用**固定 seed 采 500–1000 题**，种子写进配置，保证：
- 跨实验用同一批题（E1/E2/E3/E4/E5 可比）
- 论文可复现
- bootstrap 显著性时基于固定样本

子采样规模（建议，可调）：

| 数据集 | 原始规模 | 子采样 | 用途 |
|--------|----------|--------|------|
| MuSiQue | ~2.5万 | 1000 | 主战场，全实验共用 |
| ALCE | ~4千 | 500 | C3 引用主测 |
| FreshQA | ~12万 | 500 | C3 抗幻觉 |
| HotpotQA | ~9万 | 1000 | C1/C2 多跳 |

### 决策 4：检索 Baseline 用本地轻量栈，不碰 API

传统 RAG baseline（bge-m3 embed + FAISS + bge-reranker）和长上下文直塞 baseline **不需要 LLM 生成器以外的 API**——embedding/rerank 走本地小模型或公开 API。

- **FAISS**：纯本地，**向量库已锁定**（业界事实标准，审稿人零认知摩擦，最公正代表 chunk+embed+top-k 范式；LanceDB/Zvec/Chroma 不引入，避免"baseline 选型是否公平"争议）
- **bge-m3**：本地跑优先（~567M，GPU 友好，CPU 可跑但慢；子采样 1000 题一次性建索引可接受）
- **bge-reranker**：本地跑优先
- 长上下文 baseline：直接把检索池/全文塞进 K3/Qwen3.8 的 1M 窗口（走 ModelGateway）

**降级路径（不启用，保留作保险）**：bge-m3/reranker 本地跑不动 → 切 embedding API（硅基流动 / Jina / OpenAI text-embedding）。切换时输出维度需对齐 FAISS 索引，整个索引重建一次（缓存层兜底，不重复付费）。

这一层是"传统范式"的代表，必须存在且可复现，作为 E0/E1/E2/E4 的统一对照。

### 决策 4 补充：本地化可行性已实测验证（2026-07-26）

**硬件**：Mac mini Apple M4 / 10 核 / 16GB 统一内存

**实测结论（bge-m3 + FAISS 全本地，MPS 加速）**：

| 指标 | 实测值 |
|------|--------|
| torch 2.13.0 + MPS | ✅ 可用 |
| bge-m3 加载（首次含下载 2.2GB）| 120s，缓存后秒级 |
| 模型驻留内存 | 588 MB |
| **编码 1000 chunk** | **30.7s（31ms/chunk）** |
| embedding 维度 | 1024 |
| FAISS 建 1000 向量索引 | <0.01s |
| FAISS top-5 检索 | 334ms（含 query 编码）|
| 峰值进程内存 | 735 MB，系统余 8.3GB |

**结论：bge-m3 本地化方案可行，降级路径不启用。** 1000 题子采样建索引 ≈ 半分钟，全部四个数据集建索引几分钟内完成——是 W1 流水线最便宜的环节。真正成本全在 LLM API（K3/Qwen3.8）调用。

**外推上限（约束 E2 索引规模）**：

| 语料规模 | 预计编码 | 内存峰值 |
|----------|----------|----------|
| 1万 chunk | ~5 分钟 | ~1GB |
| 10万 chunk | ~50 分钟 | ~2-3GB |
| 100万 chunk | ~8 小时 | ~10GB ⚠️ 逼近 16GB |

→ **E2 索引上限设为 10万 chunk**（覆盖实验需求 + 留足内存余量）。E0 的 10⁶ 档走 LongContext 直塞窗口，不建索引。

**网络坑（必须写进复现说明）**：HuggingFace 直连 timeout，必须 `export HF_ENDPOINT=https://hf-mirror.com`（在 Python 启动前设置，否则 sentence-transformers 部分元数据请求仍走官方域名）。

## 四、各层详细设计

### 4.1 模型接入层 ModelGateway

**职责**：把"调 K3"和"调 Qwen3.8"统一成一个接口，屏蔽协议差异。

**对外接口（描述）**：
- `generate(model_config, messages, tools=None, **params) → Response`
  - `Response` 含：文本、工具调用、token 用量、原始 raw（便于 debug）
- `stream(...)`（流式，长输出时用）
- 内部自动走缓存（命中则不调 API）

**协议适配**：
- `protocol=openai` → 走 OpenAI SDK，`base_url` 指向模型方 endpoint
- `protocol=anthropic` → 走 Anthropic SDK
- 两套适配器实现同一接口，上层无感

**配置示例（YAML，非代码逻辑）**：
```
models:
  kimi-k3:
    protocol: openai
    base_url: <Moonshot 或第三方 OpenAI 兼容 endpoint>
    api_key_env: KIMI_API_KEY
    model_name: kimi-k3
    max_tokens: 8192
  qwen3.8:
    protocol: openai
    base_url: <DashScope 或第三方 OpenAI 兼容 endpoint>
    api_key_env: QWEN_API_KEY
    model_name: qwen3.8
    max_tokens: 8192
roles:
  generator: kimi-k3
  verifier: qwen3.8
```

**待用户确认（非 blocking）**：具体 `base_url` 与平台——你告诉我走 Moonshot 官方 / DashScope / 硅基流动 / 其他，我填进配置。

### 4.2 数据层 DataLoader

**职责**：统一加载四个数据集、固定子采样、构造 E0 检索池。

**四个加载器**：MuSiQue / ALCE / FreshQA / HotpotQA。各自解析原始格式，统一吐成内部 schema：

```
Sample:
  id: str
  question: str
  answer: str (gold)
  supporting_docs: List[Doc]   # MuSiQue/HotpotQA 有；FreshQA/ALCE 部分有
  metadata: {...}
```

**子采样**：每集按固定 seed 取 N 题，结果落盘 `subsample_{dataset}_{seed}_{n}.jsonl`，保证 W2–W4 复用同一批。

**E0 多规模检索池**（立论关键，单独说明）：
- 基于 MuSiQue 的全部支撑文档 + 干扰文档池
- 构造 4 个规模档：检索池总 token ≈ 10³ / 10⁴ / 10⁵ / 10⁶
- 每档保证：gold 支撑文档在内 + 按比例混入干扰文档
- 目的：测"长上下文直塞 vs 传统 RAG"在不同池规模下的准确率交叉点（拐点）
- 1M 窗口下 10⁶ 档可整体装入 → 拐点存在与否即 H1 的硬证据

### 4.3 方法层 Methods（W1 仅 baseline）

**TraditionalRAG**：
1. 检索池 → bge-m3 embed → FAISS 索引（建一次，缓存）
2. query → top-k 召回（k=10）→ bge-reranker 重排 → 取 top-5
3. 拼入 prompt → ModelGateway.generate → answer

**LongContext**：
1. 检索池（或全文）整体塞入 1M 窗口
2. query + 全文 → ModelGateway.generate → answer

**为 W2 预留的接口契约**（C1/C2/C3 必须满足，否则无法挂入共享层）：
- 统一签名：`method.run(sample, model_config) → Result(answer, retrieved_docs, claims, trace)`
- `trace` 字段记录工具调用/索引命中/校验过程，供评测与 appendix 用

### 4.4 评测层 Evaluator

**接入的现成工具**：
- **RAGAS**：faithfulness / answer_relevancy / context_precision / context_recall
- **ALCE 评测脚本**：citation_f1 / citation_precision（自动 span 匹配）

**自定义指标占位**（W1 只占位 + 接口，实现在 W2–W3）：
- `claim_level_citation_granularity`：每个 atomic claim 的证据映射成功率
- `cross_source_contradiction_detection_rate`：矛盾集上的检测率

**统计**：所有指标用 bootstrap（n=1000）报 95% CI；主结果要求 p<0.01。W1 先把 bootstrap 工具备好。

### 4.5 实验编排层 ExperimentRunner（最小可用版）

**职责**：把"一个实验"描述成配置，跑完落盘结果。

**实验定义（YAML）**：
```
experiment:
  name: E0_bottleneck_shift
  dataset: musique_subsample
  methods: [TraditionalRAG, LongContext]
  models: [kimi-k3, qwen3.8]
  pool_scales: [1e3, 1e4, 1e5, 1e6]
  metrics: [em, f1, ragas_faithfulness]
  sample_n: 1000
  seed: 42
```

**执行**：遍历 `methods × models × pool_scales`，对每个 sample 调 method、收 Result、喂 Evaluator、汇总指标 + CI、写 `results/{exp_name}/{timestamp}.json`。

**断点续跑**：sample 级别落盘，中断后跳过已完成项（API-only 实验的必备，否则中断=重付费）。

## 五、配置与可复现性

**单一配置源**：一份 `config.yaml` 描述模型、数据、实验。任何实验跑动 = 改配置 + 跑 runner。

**可复现三件套**：
1. 固定 seed（数据子采样、bootstrap）
2. 请求级缓存（prompt hash → 响应）
3. 实验配置 + git commit hash 一起落盘到结果目录

**论文 appendix 可直接引用**：跑某张表用的 config 文件 + 缓存 hash，审稿人可据此复现。

## 六、缓存与成本（API-only 核心约束）

| 维度 | 措施 |
|------|------|
| 重复请求 | 请求级缓存，命中不付费 |
| prompt 迭代 | prompt 加版本号入 hash，避免无意 miss 缓存 |
| 子采样 | 每 benchmark 500–1000 题（见决策 3）|
| E0 检索池 | 10⁶ 档只取必要规模，不盲目堆 token |
| 断点续跑 | sample 级落盘，中断不重付费 |
| 成本监控 | ModelGateway 记录每次调用的 token 用量 + 估算花费，日终汇总 |

**粗估（W1）**：baseline 跑 4 数据集 × 2 模型 × ~1000 题，单题 ~5–30K token，量级在百万–千万 token 级。具体取决于平台单价（待你确认）。

## 九、风险与降级

| 风险 | 降级 |
|------|------|
