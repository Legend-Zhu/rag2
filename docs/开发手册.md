## 一、模型调用（K3 / Qwen3.8）

### 1.1 K3 温度硬约束
- API 仅接受 `temperature=1.0`，传 0/0.5 直接报 400
- gateway 已用 `forced_temperature=1.0` 自动覆盖
- **可复现性靠请求级缓存**（同 prompt 命中缓存返回同结果）

### 1.2 Qwen3.8 thinking 模式强制开启
- `enable_thinking` 报 `"restricted to True"`，无法关闭
- **completion token 含 thinking 过程**，约答案可见 token 的 3-5 倍
- 这是 thesis H1/H2 的时代佐证（reasoning-first LLMs 成主流）

### 1.3 ⚠️ thinking 模式的 max_tokens 陷阱（重要）
**所有需要长输出的 LLM 调用必须 override max_tokens ≥ 16000**，否则：
- thinking 占满 completion 额度
- 真正的 JSON/答案被截断
- 解析失败但**不报错**（静默错误，最难排查）

受影响的调用：
- C2 索引构建（JSON 输出）→ 已 override `max_tokens=16000`
- C2 后端 A/C（LLM 判断输出 id 数组）→ 用 `max_tokens=500`（够）
- C3 claim 校验（JSON 输出）→ 待实现时注意
- C1 推理规划（多步）→ 每步 max_tokens 要留足 thinking 额度

### 1.4 ⚠️ 结构化输出必须用 function calling，不要文本解析（核心教训）
**永远不要让 LLM 输出自然语言 JSON 然后用正则解析**。原因：
- thinking 模式下，思考过程里**也可能有 JSON 片段**，正则误匹配
- 输出可能被截断，JSON 不闭合
- 解析失败是静默错误，难排查

**正确做法**：用 function calling，让模型把结构化结果作为工具参数传入。API 层保证 schema 合法，绕过解析。

受影响（都已改或应改）：
- C2 索引构建 → ✅ 已改用 `save_index_entries` 工具
- C2 后端 A/C（LLM 判断）→ ⚠️ 当前正则解析，应改工具调用
- C3 claim 校验 → 待实现，必须用工具调用
- C1 推理子查询 → 当前正则，可考虑工具调用

### 1.5 截断续写 loop（generate_complete）
- 不靠 brute force 调大 max_tokens，靠 loop 补全
- `finish_reason=length` 时追加 "continue" 消息让模型续写
- 配合 function calling：工具参数若被截断，重试或续写

### 1.6 ⚠️ 必须用流式输出（核心修复，2026-07-27）
**问题**：Qwen3.8 非流式请求服务端固定 300s 超时，thinking 模式 + 长输入 + 工具调用会超时挂起（客户端 ESTABLISHED 但永远等不到响应）。

**官方文档明确**："建议优先使用流式输出，可以避免超时问题"
- 文档：https://platform.qianwenai.com/docs/developer-guides/run-and-scale/streaming

**修复**：gateway 的 `_call_openai` 改用 `stream=True` + `stream_options={"include_usage": True}`
- 流式下 content / reasoning_content / tool_calls 都是增量 delta，需累积拼接
- 工具参数 `function.arguments` 分块返回，按 index 累积后才能解析 JSON
- 实测：5 文档索引构建需 372s，非流式 300s 必挂，流式能撑过

**thinking 模式的 reasoning_content**：
- 多轮对话传回 assistant 消息时**必须保留 `reasoning_content` 字段**（文档要求）
- 否则模型行为异常

**enable_thinking 开关**（正确用法）：
- `extra_body={"enable_thinking": True/False}`（不是直接传参）
- Qwen3.8 强制开启（restricted to True）
- 关闭后才能用 `tool_choice` 强制指定工具

### 1.4 配额模型
- **token plan 订阅制**（K3 和 Qwen3.8 各自独立池）
- Qwen3.8 七天配额约 33M，按周刷新
- 夜间 22:00-08:00 享 2 折起（省配额）
- "成本"= token 配额消耗，不是钱

## 二、网络与依赖

### 2.1 PyPI 大文件
- 用清华镜像：`-i https://pypi.tuna.tsinghua.edu.cn/simple --retries 5`

### 2.2 HuggingFace 模型/数据
- 必须 `export HF_ENDPOINT=https://hf-mirror.com`（直连 timeout）
- 模型缓存后必须 `export HF_HUB_OFFLINE=1`（避免元数据 HEAD 请求偶发 client closed）
- 大模型（reranker 等）用 `snapshot_download` 单独预热
- ⚠️ **hf-mirror 对 `resolve/main/` 路径会 308 重定向到 huggingface.co**，导致 `load_dataset` 失败
  - 解决：对 parquet 数据集，**curl 直连 huggingface.co 下载 parquet，pandas 读**
  - 示例：`curl -sL https://huggingface.co/datasets/{repo}/resolve/main/data/{split}-00000-of-00001.parquet -o data_raw/{name}/{split}.parquet`

### 2.3 ⚠️ 内容审查（K3 + Qwen3.8 都有）
- **MuSiQue 含 Wikipedia 人物/政治内容，K3/Qwen3.8 均会审查拒绝**（content_filter / data_inspection_failed / high risk）
- 被拒的代码会**静默降级**（catch 异常 → 空标注）——必须在结果里检测并暴露
- **解决：换纯科学/技术领域数据集**（SciQ 已验证零拒绝）
- 已知会触发拒绝的：Chai Ling（历史人物）、其他 Wikipedia 政治类内容

### 2.3 Python 3.14 兼容性
- torch 2.13.0 / datasets 5.0.0 / sentence-transformers 5.6.1 均兼容（已验证）

## 三、Mac mini M4 / 16GB

### 3.1 bge-m3 本地推理
- MPS 加速可用，31ms/chunk
- 内存峰值 735MB，余 8.3GB
- E2 索引上限 10万 chunk（再大逼近 16GB）

### 3.2 ⚠️ MPS 显存累积（重要）
- 每题 new 一个 Retriever 会累积显存，最终 OOM（19.89 GiB > 16GB 物理）
- **修复**：Retriever 全局单例，复用 embedder/reranker
- 每轮调 `torch.mps.empty_cache()`

## 五、Shell 坑

### 5.1 zsh nomatch
- `rm cache/*.json` 在无匹配文件时 zsh 报错退出（不像 bash 静默）
- **用 `rm -f`** 或 `find ... -delete`

### 5.2 后台 heredoc 不可靠
- `python3 << EOF` 在后台模式输出可能被吞
- **长任务用脚本文件 + nohup**，不用 heredoc

### 5.3 ⚠️ 环境变量与 role 混淆（重要）
- 新 shell 会话**不会继承**之前 `export` 的环境变量——每次跑都要重新设
- 测试脚本里**硬编码的 `role='kimi-k3'`** 会绕过 config 的 roles 配置
- **切换模型时**：改 config 的 `roles.generator` **不够**，还要检查脚本里是否硬编码 role
- 诊断方法：`grep "role=" tests/*.py src/rag2/experiments/*.py`
- 401（认证失败）通常不是配额问题（配额是 403）——先查 key 是否设对、role 是否指对模型

## 六、静默错误防护（设计原则）

API 的"静默错误"是实验可信度的最大敌人。gateway 层必须把所有隐式行为转成显式契约：

| 静默风险 | 防护 |
|----------|------|
| 输入超窗口被截断 | `ContextOverflowError` 显式报错 |
| 温度被 API 覆盖 | `forced_temperature` 自动处理 |
| max_tokens 截断输出 | 捕获 `finish_reason=length` 并告警 |
| thinking 占满 completion | 长输出 override `max_tokens=16000` |
| JSON 截断解析失败 | `_parse_response` 截断容错（补 `]`）|
